# ADR-0116: The coordinator edits an event's details and its equipment lines only once the request is approved, until it is Confirmed

- **Status:** Accepted; the window (Approved and Safety Review, for both), the refusal before approval pointing to a clarification or the Organiser's change request, keeping lines recorded earlier with Technical Support's outcome still open to them, and the lock sitting only in the direct-edit paths are SCRUM-110 AC1 to AC6 (the Product Owner's decision of 29 Oct); the wording, reusing the error codes, refusing the removal of an older line, Technical Support still hearing about an older line, sending the status with the equipment lines and how the web app hides its controls are defaults to review
- **Date:** 2026-10-31
- **Story:** SCRUM-110 Coordinator edits event details and equipment only once the request is approved
- **Supersedes:**
  - [ADR-0101](0101-direct-edits-stop-at-confirmed.md) decision 1 (the five editable statuses), decision 5 (the coordinator's edit while the organiser's answer is awaited), decision 7 (the equipment window left as it was) and decision 9's list of statuses the web app offers the edit in;
  - the start of [ADR-0092](0092-equipment-line-changes-reopen-the-review.md) decision 1's equipment window (submitted, under review and awaiting clarification).
- **Extends:** [ADR-0019](0019-event-equipment-lines.md), [ADR-0028](0028-review-and-decide.md), [ADR-0029](0029-clarification-requests.md)

## Context
SCRUM-110 (29 Oct) moves the start of two windows to the coordinator's approval:

1. The assigned coordinator can edit the event details (SCRUM-33) only while the event is Approved or in Safety Review.
2. An edit while Submitted, Under Review or Awaiting Clarification is refused. The message says the request has to be approved first, and that changes before then go through a clarification (SCRUM-32) or the Organiser's change request (SCRUM-56). The one exception is the amendment the coordinator records with a clarification response (SCRUM-32 AC2).
3. Equipment lines (SCRUM-37) can be added, edited or removed only while Approved or in Safety Review, so Technical Support Staff are never notified about an event that hasn't been approved.
4. Lines already recorded on an event that isn't approved yet are kept as they are, and Technical Support can still record their outcome.
5. A Confirmed event is still changed only through a change request (SCRUM-56, SCRUM-57).
6. The lock is on direct edits only. Approving a change request (SCRUM-57) applies it in any status where one can be raised, including before approval.

The Product Owner decided this on 29 Oct: venue requests (SCRUM-42) and the safety check (SCRUM-97) already waited for Approved, and equipment never did only because SCRUM-37 was written before Approved existed. The customer's answers ("before the final confirmed status", Week 9; "at any time before confirmation", Week 4) set where the windows end, which stays at Confirmed.

On `main` before this ADR, `EDITABLE_STATUSES` and `EQUIPMENT_EDITABLE_STATUSES` both held submitted, under review, awaiting clarification, approved and Safety Review (ADR-0101, ADR-0092).

**SCRUM-32 AC2 on `main`.** Jira's SCRUM-32 AC2 (changed 17 Oct) has the coordinator record the Organiser's response and make any amendments. That action is not built: SCRUM-32's rework is still open. The only amendment that rides with a clarification response on `main` is the organiser's `POST /api/events/requests/<reference>/resubmit` (ADR-0029). It has its own check (the request must be awaiting clarification) and applies its amendments through `_record_field_changes`; it never read `EDITABLE_STATUSES`. What did read it was the coordinator's ordinary edit, which ADR-0101 decision 5 allowed while the answer was awaited so the coordinator could record amendments that way.

## Decision
1. **`EDITABLE_STATUSES` is `approved` and `safety_review`** (AC1). The order of the checks is unchanged: reference `404`, ownership `404`, status `409`, payload `400` (ADR-0025 decision 8). A draft is still never found by staff (`404`, ADR-0024).
2. **Before approval the edit is refused, pointing the way changes go then** (AC2). A request in `AWAITING_DECISION_STATUSES` (submitted, under review, awaiting clarification: SCRUM-31's own set, moved up to the module's constants so "not approved yet" has one definition) gets `409 request_not_editable` with: "An event request can only be edited once it is approved. Until then, changes go through a clarification or the organiser's change request." **Default to review:** the wording, and keeping the one error code: the web app shows the message and doesn't branch on codes (ADR-0101 decision 4's reasoning).
3. **Confirmed and the finished statuses keep their refusals** (AC5): "A confirmed event can only be changed through a change request." and "An event request can only be edited before it is confirmed, and not once it is rejected or cancelled." The second is only ever shown for a completed, cancelled or rejected event now, for which it is still true, so it is left alone.
4. **Equipment lines change only while Approved or in Safety Review** (AC3). `EQUIPMENT_EDITABLE_STATUSES` is `approved` and `safety_review`. Adding, changing or removing a line before approval gets `409 equipment_not_editable` with: "Equipment can only be added, changed or removed once the event request is approved. Until then, changes go through a clarification or the organiser's change request." The refused add saves nothing, so nothing tells Technical Support. Confirmed and after keep ADR-0092's message. The two sets keep separate constants with the same values, as ADR-0101 decision 7 reasoned. **Default to review:** the wording, its ending shared with the edit's (`CHANGES_BEFORE_APPROVAL`), and reusing the code.
5. **A line recorded before approval stays as it is** (AC4). Nothing deletes, moves or migrates the lines already on events that aren't approved yet. Technical Support still list them (SCRUM-38's list is unchanged) and record or revise their outcome: `record_equipment_outcome` keeps its own status rule (only completed, cancelled and rejected events refuse an outcome, SCRUM-48 AC8). The first decision on such an event is never locked by its lines (ADR-0028 decision 10 only blocks a change of decision).
   - **Default to review:** the coordinator can't remove such a line before approval either, since AC3 locks removal too. It waits for the approval, or goes with a rejection.
   - **Default to review:** an organiser's amendment that could affect equipment (`/resubmit`) still asks Technical Support to recheck an event's older lines (ADR-0025, ADR-0029), although the event isn't approved: they already own those lines (AC4), and no new line can reach them before approval.
6. **The lock lives only in the direct-edit paths** (AC6): `_event_request_editable_by`, the edit's own lookup, and `_event_request_with_editable_equipment`, the coordinator's own line changes. What applies a change carries no status check: `_record_field_changes` for the event's fields, and the line helpers (`_reopen_changed_line`, `_record_line_change`, `_clear_outcome`) for its lines. So:
   - the organiser's `/resubmit` keeps applying its amendments while the answer is awaited, through `_record_field_changes` and its own check (its tests are unchanged and pass);
   - **when SCRUM-56/57 are built,** approving a change request should apply it through those helpers under its own status rule ("any status where one can be raised"), not through `update_event_request` or the line services, which would refuse it before approval.
7. **SCRUM-32 AC2's coordinator amendment is not built, and isn't built here.** Since ADR-0101 decision 5 is superseded, the coordinator can no longer record an amendment through the ordinary edit while the answer is awaited. Until SCRUM-32's rework adds the coordinator's "record the response" action, amendments before approval come only through the organiser's `/resubmit` (the API takes them; the web app's answer form sends the response alone). That action should check `awaiting_clarification` itself and apply its amendments through `_record_field_changes`, as `/resubmit` does, so this lock never touches it.
   - **Open, needs the Product Owner:** this leaves AC2's exception partly met. The Product Owner's 29 Oct comment on SCRUM-32 makes the coordinator's amendment with a clarification response "the only way" they change event details before approval, and until SCRUM-32's rework the coordinator has no way at all. Either the Product Owner accepts that gap until the rework lands, or the rework merges before or with this change.
8. **The web app offers each change only where the backend accepts it** (supersedes ADR-0101 decision 9's list).
   - The event page's "Edit details" section shows for the assigned coordinator only while the event is Approved or in Safety Review. The edit form still shows the backend's refusal in its own words if one comes back, for example on an event opened by its link.
   - **Default to review:** `GET /api/events/requests/<reference>/equipment` now names the event's `status` beside its date and times (`EVENT_LIST_FIELDS`, as the event lists send it; additive), so the Equipment page shows its coordinator the Add form and each line's Change and Remove only while the lines can change. Otherwise it says when they can: "Equipment can be added, changed or removed once the request is approved, until the event is confirmed." Technical Support's outcome controls don't depend on the status.
9. **The mock and the contract tests follow** (CONVENTIONS §14). `eventEdits.ts` and `equipmentLines.ts` refuse before approval with the backend's messages, and the equipment lines mock answers the status. The tests that edit the mock's Partner Summit, which it seeds under review, approve it first through the mock's decide endpoint; the e2e journey approves it on the page before editing. The integration tests check both refusals, the edit once approved and the listed status against the real backend.
10. **No migration and no data change.**

## Consequences
- A coordinator who used to fix a typo or note before approving now asks through a clarification, or approves first. Before approval, the Organiser's change request (SCRUM-56) is the other way, once it is built.
- Technical Support hear about an event's equipment only once it is approved, except for lines recorded before this change (decision 5).
- Until SCRUM-32's rework, the coordinator can't record amendments with a clarification response themselves (decision 7). The organiser's `/resubmit` still can.
- SCRUM-56/57 must apply an approved change request through the shared helpers, not the direct-edit services (decision 6).

## Revisit when
- SCRUM-32's rework builds the coordinator's "record the response" action: it carries the amendments of AC2's exception (decision 7).
- SCRUM-56/57 are built: check the apply path skips the direct-edit lookups (decision 6).
- The Product Owner wants an older line removable before approval, or Technical Support not told about one (decision 5).
