# ADR-0116: The coordinator edits an event's details and its equipment lines only once the request is approved, until it is Confirmed

- **Status:** Accepted; the window (Approved and Safety Review, for both), the refusal before approval pointing to a clarification or the Organiser's change request, the one exception for the coordinator's amendments with a clarification response, keeping lines recorded earlier with Technical Support's outcome still open to them, and the lock sitting only in the direct-edit paths are SCRUM-110 AC1 to AC6 (the Product Owner's decision of 29 Oct); delivering that exception through the direct edit while the answer is awaited until SCRUM-32's rework, the wording, reusing the error codes, refusing the removal of an older line, Technical Support still hearing about an older line, sending the status with the equipment lines and how the web app hides its controls are defaults to review
- **Date:** 2026-10-31
- **Story:** SCRUM-110 Coordinator edits event details and equipment only once the request is approved
- **Supersedes:**
  - [ADR-0101](0101-direct-edits-stop-at-confirmed.md) decision 1 (the five editable statuses: submitted and under review leave them), decision 7 (the equipment window left as it was) and decision 9's list of statuses the web app offers the edit in. ADR-0101 decision 5 (the coordinator's edit while the organiser's answer is awaited) stays: it carries SCRUM-110 AC2's exception (decision 7 below);
  - the start of [ADR-0092](0092-equipment-line-changes-reopen-the-review.md) decision 1's equipment window (submitted, under review and awaiting clarification).
- **Extends:** [ADR-0019](0019-event-equipment-lines.md), [ADR-0028](0028-review-and-decide.md), [ADR-0029](0029-clarification-requests.md)

## Context
SCRUM-110 (29 Oct) moves the start of two windows to the coordinator's approval:

1. The assigned coordinator can edit the event details (SCRUM-33) only while the event is Approved or in Safety Review.
2. An edit while Submitted, Under Review or Awaiting Clarification is refused. The message says the request has to be approved first, and that changes before then go through a clarification (SCRUM-32) or the Organiser's change request (SCRUM-56). The one exception is the amendment the coordinator records with a clarification response (SCRUM-32 AC2).
3. Equipment lines (SCRUM-37) can be added, edited or removed only while Approved or in Safety Review, so Technical Support Staff are never notified about an event that hasn't been approved.
4. Lines already recorded on an event that isn't approved yet are kept as they are, and Technical Support can still record their outcome.
5. A Confirmed event is still changed only through a change request (SCRUM-56, SCRUM-57).
6. The lock is on direct edits only. Approving a change request (SCRUM-57) applies it in any status where one can be raised, including before approval.

The Product Owner decided this on 29 Oct: venue requests (SCRUM-42) and the safety check (SCRUM-97) already waited for Approved, and equipment never did only because SCRUM-37 was written before Approved existed. The customer's answers ("before the final confirmed status", Week 9; "at any time before confirmation", Week 4) set where the windows end, which stays at Confirmed.

On `main` before this ADR, `EDITABLE_STATUSES` and `EQUIPMENT_EDITABLE_STATUSES` both held submitted, under review, awaiting clarification, approved and Safety Review (ADR-0101, ADR-0092).

**SCRUM-32 AC2 on `main`.** Jira's SCRUM-32 AC2 (changed 17 Oct) has the coordinator record the Organiser's response and make any amendments. That action is not built: SCRUM-32's rework is still open. The only amendment that rides with a clarification response on `main` is the organiser's `POST /api/events/requests/<reference>/resubmit` (ADR-0029). It has its own check (the request must be awaiting clarification) and applies its amendments through `_record_field_changes`; it never read `EDITABLE_STATUSES`. What did read it was the coordinator's ordinary edit, which ADR-0101 decision 5 allows while the answer is awaited so the coordinator can record amendments that way. The Product Owner's comment on SCRUM-32 (29 Oct) says that before approval, the amendment the coordinator records with a clarification response is the only way the coordinator changes event details.

## Decision
1. **`EDITABLE_STATUSES` is `awaiting_clarification`, `approved` and `safety_review`** (AC1; awaiting clarification for AC2's exception, decision 7). The lookup checks the allowed statuses first, then the refusals. The order of the checks is unchanged: reference `404`, ownership `404`, status `409`, payload `400` (ADR-0025 decision 8). A draft is still never found by staff (`404`, ADR-0024).
2. **Submitted or under review, the edit is refused, pointing the way changes go then** (AC2). A request in `AWAITING_DECISION_STATUSES` (SCRUM-31's own set, moved up to the module's constants so "not approved yet" has one definition) that isn't in `EDITABLE_STATUSES`, so submitted or under review, gets `409 request_not_editable` with: "An event request can only be edited once it is approved. Until then, changes go through a clarification or the organiser's change request." The wording still holds with the exception: from Under Review the coordinator asks for a clarification, and the amendments come with the answer (decision 7). **Default to review:** the wording, and keeping the one error code: the web app shows the message and doesn't branch on codes (ADR-0101 decision 4's reasoning).
3. **Confirmed and the finished statuses keep their refusals** (AC5): "A confirmed event can only be changed through a change request." and "An event request can only be edited before it is confirmed, and not once it is rejected or cancelled." The second is only ever shown for a completed, cancelled or rejected event now, for which it is still true, so it is left alone.
4. **Equipment lines change only while Approved or in Safety Review** (AC3). `EQUIPMENT_EDITABLE_STATUSES` is `approved` and `safety_review`. Adding, changing or removing a line before approval gets `409 equipment_not_editable` with: "Equipment can only be added, changed or removed once the event request is approved. Until then, changes go through a clarification or the organiser's change request." The refused add saves nothing, so nothing tells Technical Support. Confirmed and after keep ADR-0092's message. The two sets are separate constants, as ADR-0101 decision 7 reasoned, and now differ: awaiting clarification is in the edit's set only, since AC3 locks lines in every status before approval and the exception (decision 7) covers the event's details, not its lines. **Default to review:** the wording, its ending shared with the edit's (`CHANGES_BEFORE_APPROVAL`), and reusing the code.
5. **A line recorded before approval stays as it is** (AC4). Nothing deletes, moves or migrates the lines already on events that aren't approved yet. Technical Support still list them (SCRUM-38's list is unchanged) and record or revise their outcome: `record_equipment_outcome` keeps its own status rule (only completed, cancelled and rejected events refuse an outcome, SCRUM-48 AC8). The first decision on such an event is never locked by its lines (ADR-0028 decision 10 only blocks a change of decision).
   - **Default to review:** the coordinator can't remove such a line before approval either, since AC3 locks removal too. It waits for the approval, or goes with a rejection.
   - **Default to review:** an amendment that could affect equipment, the organiser's (`/resubmit`) or the coordinator's while the answer is awaited (decision 7), still asks Technical Support to recheck an event's older lines (ADR-0025, ADR-0029), although the event isn't approved: they already own those lines (AC4), and no new line can reach them before approval.
6. **The lock lives only in the direct-edit paths** (AC6): `_event_request_editable_by`, the edit's own lookup, and `_event_request_with_editable_equipment`, the coordinator's own line changes. What applies a change carries no status check: `_record_field_changes` for the event's fields, and the line helpers (`_reopen_changed_line`, `_record_line_change`, `_clear_outcome`) for its lines. So:
   - the organiser's `/resubmit` keeps applying its amendments while the answer is awaited, through `_record_field_changes` and its own check (its tests are unchanged and pass);
   - **when SCRUM-56/57 are built,** approving a change request should apply it through those helpers under its own status rule ("any status where one can be raised"), not through `update_event_request` or the line services, which would refuse it before approval.
   - Nothing applies a change request yet, so `tests/events/test_changes_apply_in_any_status.py` calls those helpers directly on a submitted, an under-review and a confirmed event, and checks each applies the change and writes it to the history. A status check added to any of them fails there.
7. **SCRUM-32 AC2's exception is the coordinator's direct edit while the answer is awaited, until SCRUM-32's rework.** ADR-0101 decision 5 stands: while the event is Awaiting Clarification, its assigned coordinator may edit its details through the ordinary edit (`PATCH /api/events/requests/<reference>`), and the status stays Awaiting Clarification. That is how `main` records the amendments that come with the organiser's response today, and it is what the Product Owner's comment of 29 Oct on SCRUM-32 assumes. Equipment lines are not part of the exception (AC3, decision 4). When SCRUM-32's rework builds the coordinator's "record the response" action, which also moves the event back to Under Review, it takes the amendments in: it should check `awaiting_clarification` itself and apply them through `_record_field_changes`, as `/resubmit` does, and Awaiting Clarification then leaves `EDITABLE_STATUSES` and the web app's list (decision 8).
   - **Default to review:** delivering the exception through the direct edit until then. The edit isn't tied to a response, so the coordinator can amend before the organiser answers, as on `main`; the history shows each change and who made it (ADR-0101 decision 5).
8. **The web app offers each change only where the backend accepts it** (supersedes ADR-0101 decision 9's list).
   - The event page's "Edit details" section shows for the assigned coordinator only while the event is Awaiting Clarification (decision 7), Approved or in Safety Review. The edit form still shows the backend's refusal in its own words if one comes back, for example on an event opened by its link.
   - **Default to review:** `GET /api/events/requests/<reference>/equipment` now names the event's `status` beside its date and times (additive: the same fields as an event list row, `EVENT_LIST_FIELDS`), so the Equipment page shows its coordinator the Add form and each line's Change and Remove only while the lines can change. Otherwise it says when they can: "Equipment can be added, changed or removed once the request is approved, until the event is confirmed." Technical Support's outcome controls don't depend on the status.
9. **The mock and the contract tests follow** (CONVENTIONS §14). `eventEdits.ts` and `equipmentLines.ts` refuse before approval with the backend's messages, `eventEdits.ts` lets the edit through while the answer is awaited, and the equipment lines mock answers the status. The tests that edit the mock's Partner Summit, which it seeds under review, approve it first through the mock's decide endpoint; the e2e journey approves it on the page before editing. The integration tests check both refusals, the amendment while the answer is awaited, the edit once approved and the listed status against the real backend.
10. **No migration and no data change.**

## Consequences
- A coordinator who used to fix a typo or note on a submitted or under-review request now asks through a clarification, and records the change while the answer is awaited, or approves first. Before approval, the Organiser's change request (SCRUM-56) is the other way, once it is built.
- Technical Support hear about an event's equipment only once it is approved, except for lines recorded before this change (decision 5).
- Until SCRUM-32's rework, the coordinator records amendments with a clarification response through the direct edit while the answer is awaited (decision 7). The organiser's `/resubmit` still can too.
- SCRUM-56/57 must apply an approved change request through the shared helpers, not the direct-edit services (decision 6).

## Revisit when
- SCRUM-32's rework builds the coordinator's "record the response" action: it carries the amendments of AC2's exception, and Awaiting Clarification leaves `EDITABLE_STATUSES`, the mock's list and the web app's (decision 7).
- SCRUM-56/57 are built: check the apply path skips the direct-edit lookups (decision 6).
- The Product Owner wants an older line removable before approval, or Technical Support not told about one (decision 5).
