# ADR-0040: Technical Support records how much of an equipment request can be met; the status is derived from the quantity provided

- **Status:** Accepted; the coordinator's notice gains the outcome and the note in [ADR-0055](0055-booking-and-equipment-notices.md); the deferred safety check AC (now AC7) is built in decision 14; a rejected, cancelled or completed event refuses an outcome (AC8) in decision 15; the stale outcome on a changed line settled by [ADR-0092](0092-equipment-line-changes-reopen-the-review.md), which clears a changed line's outcome instead of refusing a quantity below it; a note given with a fulfilled outcome is kept (decision 5, revised 2026-10-25)
- **Date:** 2026-10-13
- **Story:** SCRUM-48 Record the outcome of an equipment review

## Context
SCRUM-48 lets Technical Support staff record, line by line, how much of a requested equipment line they can provide: all of it (fulfilled), some of it (partially fulfilled, with the shortfall) or none of it (unavailable, with a reason). The coordinator is told, the outcome can be revised, and a revised outcome after the Operational Safety Check forces a new check. The ACs leave open where the outcome lives, who owns the status, what the shortfall is, when a note is required, who is notified and what happens to the Technical Support queue.

## Decision
1. **The outcome belongs to the line, not to a reservation.** `EquipmentReservation` rows (SCRUM-46) record what was actually held, keyed by event and type with no link to a line. The outcome is Technical Support's statement about a request, which may differ from reservations (they can declare "unavailable" without reserving anything). So it is stored on `EventEquipmentLine` (`provided_quantity`, `outcome_note`, `reviewed_by`, `reviewed_at`), not derived from reservations. Migration `0024_add_equipment_outcome` (file `0024_add_equipment_review_outcome.py`) adds the columns and the three enum values; the revision id is shortened because a longer one exceeded the `alembic_version` column's 32 characters.
2. **`provided_quantity` is the source of truth; the status is derived.** The service computes the status: `provided == quantity` is `fulfilled` (AC2), `0 < provided < quantity` is `partially_fulfilled` (AC1), `provided == 0` is `unavailable` (AC3). The caller never sends a status, so the two can never disagree. A `provided_quantity` above the line's `quantity` is a `400`.
3. **The shortfall is derived, never stored:** `quantity - provided_quantity` (AC1). It is a different quantity from `EquipmentAvailability.shortfall` in the equipment module, which measures availability against a request, so that name is not reused on the line.
4. **`provided_quantity IS NULL` means "no outcome recorded yet".** SCRUM-97 and SCRUM-49 gate Safety Review on every equipment request having an outcome, so `lines_without_outcome` and `all_outcomes_recorded` expose that seam by name and those stories do not re-derive it.
5. **A note is required whenever `provided < quantity`, and optional for a fulfilled outcome.** AC3 requires a reason when nothing is available, and AC1 shows a note beside a partial outcome. A fulfilled outcome needs none, but one given with it is kept (AC2: "a note is optional"): it is saved on the line, written to the history entry, shown to staff wherever the note is shown, and sent in the coordinator's notice ([ADR-0055](0055-booking-and-equipment-notices.md) decision 5). A blank or whitespace-only note counts as missing. Each recording replaces the note rather than merging with it, so a revision sent with no note clears the earlier one, and a stale reason never outlives the outcome it explained. The story has since settled this (see decision 13).
   - *Revised 2026-10-25.* The first version threw away a note sent with a fulfilled outcome, reading "optional" as "never kept". That lost what Technical Support wrote (for example which units are spares), so the note is now kept. The mock backend does the same.
   - *Default to review:* the outcome form opens with the line's current note filled in (ADR-0077). Revising a partial outcome to a full one therefore keeps the old reason unless Technical Support clear it. That follows "the screen sends what was typed", and they can see the note before saving.
6. **The coordinator is notified on every recorded outcome,** not only an unavailable one. AC3 names the notification explicitly, but SCRUM-97's team assumption says any outcome Technical Support records, including partial or unavailable, counts as their decision and the coordinator is notified of it (SCRUM-48). The story has since settled this (see decision 13).
7. **An outcome can be revised with no guard (AC5, now AC6),** other than decision 15's closed events. Recording again overwrites the columns and writes another history entry (`EventHistoryKind.EQUIPMENT_OUTCOME_RECORDED`), so the trail shows the revision. There is no "already recorded" conflict. The history entry is internal: it is hidden from organisers (`INTERNAL_ONLY_KINDS`).
8. **Recording an outcome takes the line off Technical Support's queue.** `list_equipment_requests_awaiting_action` filters on the `requested` status, so a line with an outcome drops out of it. This is the one existing behaviour the change alters, and it has a test.
9. **Where the outcome is shown.** `POST /api/events/requests/<reference>/equipment/<line_id>/outcome` (endpoint `events.record_outcome`, `technical_support_staff`) returns the line with its outcome. The outcome fields (provided quantity, shortfall, note, reviewer, time) also appear on the equipment list (`GET .../equipment`). The organiser's event detail (`EventRequestDetailSchema`) shows each line's status but not the provided quantity, shortfall, note, reviewer or time; a later story shares those.
10. **A line id belonging to another event is a `404`,** and an Event Coordinator calling the route is a `403`; only Technical Support records an outcome.
11. **Deferred acceptance criteria, each with its owner.**
    - AC6 (a revised outcome after the Operational Safety Check forces a new check): **SCRUM-97** and **SCRUM-98**, because Safety Review does not exist yet. *(Built once they landed: decision 14. The AC is now AC7.)*
    - Notifications beyond the coordinator: **SCRUM-50**.
12. **Known gaps, each a default for the team to review (the organiser's detail page not showing the outcome is in decision 9).**
    - **Changing a line after an outcome is recorded can leave the outcome stale.** Lowering the quantity below `provided_quantity` is refused with a `400` on `quantity` (the database check would otherwise fire). Raising the quantity is allowed and leaves a `fulfilled` status beside a positive shortfall, and removing the line discards its outcome. A follow-up ticket for the team to raise in Jira: decide whether to block those edits once an outcome exists or to reset the outcome. **Settled:** [ADR-0092](0092-equipment-line-changes-reopen-the-review.md) (SCRUM-37) clears a changed line's outcome and releases a removed line's reservations, so the outcome can no longer go stale.
    - **`all_outcomes_recorded` returns `True` for an event with no equipment,** because no line is missing an outcome. SCRUM-97 and SCRUM-49 must decide whether an event with no equipment passes the Safety Review gate; this is what "every request has an outcome" means for zero requests.
    - **An outcome can be recorded on an event in any non-draft status,** including rejected, cancelled and completed, and the coordinator is still notified. A follow-up ticket for the team to raise in Jira: decide which statuses accept an outcome. **Settled:** the story has since gained AC8, which refuses an outcome on a rejected, cancelled or completed event (decision 15).
13. **Defaults to review (not agreed with the team):** the second gap in decision 12 (ADR-0092 settled the first, AC8 the third). **Agreed:** decisions 5 and 6, which the story's "Changed after review" note and outcome note clarification settled: AC1 and AC3 require a note for a partially fulfilled or unavailable outcome, AC2 makes it optional (so kept when given) for a fulfilled one, and AC4 notifies the coordinator once for every outcome recorded or revised.
14. **A revision after the safety check withdraws the approval (AC7).** A revision is an outcome recorded on a line that already had one (`provided_quantity` was set), the same thing decision 7 calls a revision. If the Safety Officer has approved the event, the outcome's own commit also writes a `safety_approval_withdrawn` history entry through `withdraw_safety_approval`, with the Technical Support user as actor and `details = {"equipment_line_id", "equipment_type_name", "previous_provided_quantity"}`, the quantity the approved outcome promised; an event in Safety Review or Confirmed goes back to Approved ([ADR-0087](0087-withdrawn-safety-approval-returns-the-event-to-approved.md)). The entry is internal-only, like the outcome entry beside it. The coordinator gets the one outcome notice AC4 already sends, and nothing more. A first outcome withdraws nothing: an event only reaches the Safety Officer once every line has an outcome (SCRUM-97), so a first outcome is never something they approved. **Default to review:** every revision counts, even one that records the same quantity and note again, since decision 7 has no "unchanged" case either.
15. **A rejected, cancelled or completed event refuses an outcome (AC8).** Recording one, first or revised, on an event whose status is in `EQUIPMENT_NOT_NEEDED_STATUSES`, the set the Technical Support queue (ADR-0022) and reservations (ADR-0037) already treat as events that won't run, is a `409 conflict` whose message names the event's own status: "An equipment outcome can't be recorded for an event that is completed, cancelled or rejected; this one is cancelled." (`OUTCOMES_CLOSED_MESSAGE`, in the "…; this one is {status}." form the other status refusals use). It is refused before anything is written, so the line keeps its last outcome, and there is no history entry, no notice to the coordinator and no safety approval withdrawn. A rejected event keeps the outcome it had, as the story's closed event clarification asks. The checks run in this order: the body (`400`), the event (`404`), its status (`409`), the line (`404`), then the quantity and note (`400`), so a line id of another event on a closed event is the `409`. The error code is the general `conflict`, as the coordinator's "only an approved event can have a venue booking request" refusal is, because no screen needs to tell it apart: the outcome form shows the message. **Agreed:** the Product Owner confirmed AC8 as built here: the three statuses, the `409` naming the event's status, and nothing saved or sent. **Defaults to review:** the general `conflict` error code and the order of the checks, which AC8 doesn't settle.

## Consequences
- The status can never disagree with the quantities, and the shortfall needs no migration to correct.
- An event that won't run can't gain or change an outcome, so its equipment record stays as it was when it closed.
- Safety Review stories gate on `lines_without_outcome` / `all_outcomes_recorded` without new queries.
- Until the stale-outcome ticket is settled, a coordinator's edit to a line can make a recorded outcome misleading.
- The migration's downgrade loses recorded outcomes: it resets every line with an outcome to `requested`, nulls the four outcome columns, and deletes the `equipment_outcome_recorded` history entries and notifications.
