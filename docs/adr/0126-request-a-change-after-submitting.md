# ADR-0126: An organiser asks for a change to a submitted event through a change request

- **Status:** Accepted; the statuses, the fields, saving the values when raised, locking the event's row, one Pending request at a time, withdrawing only a Pending one and withdrawing on cancellation are the story's (SCRUM-56 ACs and notes); the rest are defaults to review
- **Date:** 2026-11-01
- **Story:** SCRUM-56 Request a change after submitting my event
- **Extends:** [ADR-0025](0025-event-edits-significant-changes-and-history.md) (what an edit checks, and the history form of a value), [ADR-0012](0012-event-status-model.md) and [ADR-0020](0020-organisers-see-their-organisations-events.md) (who may see an event), [ADR-0015](0015-in-app-notifications.md), [ADR-0120](0120-lead-oversight-active-events-and-every-coordinator.md) (reading a row under a lock)

## Context
Once an event is submitted the organiser can't edit it (SCRUM-56 AC3); the coordinator's edit is SCRUM-33's, and only from Approved (SCRUM-110, ADR-0116). SCRUM-56 lets the organiser who submitted an event ask for a change to its date, start and end time, expected attendance, venue requirements, equipment requirements or programme information, saying what should change and why, while it is Submitted to Confirmed (AC1, AC2). The request waits as Pending for the coordinator, who decides it in SCRUM-57; the event keeps its details until then (AC3, AC4). The coordinator is told (AC5). Refusals say which rule stopped the organiser (AC6), only one request may wait at a time (AC7), a Pending one can be withdrawn (AC8), and cancelling the event (SCRUM-61) withdraws it (AC9). The story's notes ask for each field's value to be saved when the request is raised, so SCRUM-57 can tell whether the event changed since, and for raising and withdrawing to lock the event's row.

The ACs leave the shape of the request, the API, the checks' order and wording, the notices' text and the screen open.

## Decision
1. **Change requests live in the events module,** in a new `event_change_requests` table (migration 0053): the event, who raised it, `requested_values` and `previous_values` (JSON, keyed by field), the `reason`, a `status` (`event_change_request_status`: `pending`, `approved`, `rejected`, `withdrawn`), `raised_at`, and `withdrawn_at` and `withdrawal_note` once withdrawn. A check constraint makes a Withdrawn row carry `withdrawn_at`. They share the event's row lock and SCRUM-57 applies them with the events module's own helpers, so they don't get a module of their own. `approved` and `rejected` exist now so SCRUM-57 needs no enum migration; nothing in SCRUM-56 sets them.
2. **The requestable fields** are `proposed_date`, `end_date`, `start_time`, `end_time`, `expected_attendance`, `venue_requirements`, `equipment_requirements` and `programme_notes`. "The date" includes the end date, since an event may end on a later day (ADR-0002), and "programme information" is `programme_notes`. Anything else, `status` included, is refused as an unknown field: cancelling is SCRUM-61's.
3. **The body is flat,** `{"reason": ..., <field>: <new value>, ...}`, as the clarification answer sends its response. Each value is checked as the coordinator's edit checks it (ADR-0025): the timing rules against the event's saved values, no date in the past, an attendance of at least 1, and blank text read as asking to clear it. A date moved on its own takes the end date with it, keeping the event's length.
4. **"What should change" is at least one field whose value differs from the event's.** A value the event already has is dropped, as an edit drops it, and a request that would change nothing is a `400` "Say what should change: give at least one of the event's details a new value." The reason is required, not null and not blank: "Say why the change is needed."
5. **The values are saved in the history's form** (ADR-0025): a date `"2026-11-20"`, a time `"10:00:00"`, a number, text or `null`. `previous_values` holds each requested field's value when the request was raised (the story's note).
6. **One Pending request per event is enforced by the database only:** a partial unique index `uq_event_change_requests_pending` on `event_request_id` where `status = 'pending'`. There is no check before the save to drift from it; the `IntegrityError` becomes a `409 conflict`, "A change request is already waiting for the coordinator. Withdraw it, or wait for their decision, before raising another." (AC7). Any other integrity error is raised as it is.
7. **Raising and withdrawing read the event `FOR UPDATE`** (the story's note), with `populate_existing` as the Lead's assignment does (ADR-0120), so a status check, a withdrawal or a SCRUM-57 decision committed at the same moment is seen.
8. **The checks run in this order:** the organiser's organisation and the reference (`403` without an organisation, `404` for an event they can't see, ADR-0012, ADR-0020), the owner, the status, the body, something to change, then the Pending index. A colleague in the same organisation can see the event, so they get `403 not_event_organiser`, "Only the organiser who submitted this event can request a change to it or withdraw one.", rather than a `404`. A status outside Submitted to Confirmed is `409 change_request_not_allowed`, naming it: "A change can't be requested for a draft event." (AC6).
9. **Routes:** `POST /api/events/requests/<reference>/change-requests` (`201`) and `POST /api/events/requests/<reference>/change-requests/<id>/withdraw` (`200`, no body), Event Organisers only. Both answer the request as the record shows it. The id is in the path, as an equipment line's is.
10. **Withdrawing** is for the event's own organiser and a Pending request only; anything else is `409 change_request_not_pending`, naming its status (AC8). An id the event doesn't have is `404`, "Change request not found."
11. **The record shows `change_requests`,** oldest first, to the organiser and to the assigned coordinator: `id`, `status`, `changes` (`field`, `previous_value`, `requested_value`), `reason`, `raised_by` (a name, never an id), `raised_at`, `withdrawn_at` and `withdrawal_note`, times in business time (ADR-0009). The read-only staff record doesn't show them yet; SCRUM-57 decides who else needs them.
12. **No history entries:** the request and its status are on the record, and the event's history records changes to the event itself, which a request doesn't make (AC3). SCRUM-57 writes the history when an approved request changes the event.
13. **The notices** go to the event's assigned coordinator, through the helper the other coordinator notices use (an unassigned event logs a warning and tells nobody): `change_request_raised`, with the fields and the reason as its `detail` ("Changes to start time, expected attendance. Reason: ..."), and `change_request_withdrawn`, with no detail (AC5, AC8). Both kinds are added to `notification_kind` by migration 0053.
14. **Cancelling withdraws the Pending request** through `withdraw_pending_change_request_on_cancel(event_id, *, session)`, for SCRUM-61 to call inside its own cancel transaction with the event's row already locked: it commits nothing, notifies nobody (the cancellation tells the coordinator about the event) and sets the note "Withdrawn because the event was cancelled." (AC9). An event with no Pending request is left alone. SCRUM-61 is not on main yet, so AC9's trigger waits for it.
15. **The web app** shows the change requests on the event's page, each with its status, every change as "9:00 am → 10:00 am", why, who raised it and when, and once withdrawn when and any note; the organiser has a "Withdraw change request" button on a Pending one. A "Request a change" form sits under them for the organiser in the statuses the backend takes one in, opened with the event's values; only what differs is sent. The form stays while a request is Pending, so the backend's own AC7 message is what the organiser sees, not a copy of it. Every refusal shows as the backend words it. The coordinator sees the list but no form and no button.

## Consequences
- SCRUM-57 reads `previous_values` against the event to spot a stale request, sets `approved` or `rejected` under the same row lock, and adds its own decision columns.
- SCRUM-61 must call `withdraw_pending_change_request_on_cancel` inside its cancel transaction, or AC9 isn't met.
- The frontend's `EventRecord` type gains a required `change_requests`, so every typed fixture carries one; the mock backend keeps change requests in `changeRequestStore.ts` and checks values with the edit mock's own rules.
- Migration 0053 points at 0050 (SCRUM-60), main's head when it was written. Whichever of the open migrations numbered 0051 and 0052 merges first, this one is renumbered and re-pointed.

## Revisit when
- SCRUM-57 needs the staff record, the history or another role to see change requests.
- The Product Owner wants more than one request waiting, or other fields to be requestable.
