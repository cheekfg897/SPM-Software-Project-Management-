# ADR-0120: An active event has a coordinator, the workload lists every Event Coordinator with a count, and the first of two simultaneous assignments is kept

- **Status:** Accepted. Decisions 1, 2 and 4 follow the Jira ACs as rewritten on 15 to 17 Oct. Decision 3 (the backend sends the count) and decisions 5 to 7 are the team's decisions (31 Oct). Decisions 8 and 9 are defaults for the reviewer.
- **Date:** 2026-10-31
- **Story:** SCRUM-96 Lead reassigns events and oversees coordinator assignments (AC1, AC2, AC3); SCRUM-95 Queue new requests for the Lead and assign a coordinator (the AC added for several Leads, and the rule that an event is in the queue or the active list, never both)
- **Supersedes:** [ADR-0041](0041-lead-oversight-and-reassignment.md) decision 5's "submitted events nobody holds yet are active" and decision 6's "a coordinator with no active event is left out"; [ADR-0062](0062-lead-oversight-page.md) decisions 2 (the "Not assigned" row) and 4 (no count on the page); [ADR-0036](0036-event-coordinator-lead.md)'s "last write wins" when two Leads assign one request at once
- **Extends:** [ADR-0084](0084-venue-booking-requests-lock-the-decision.md) and [ADR-0037](0037-equipment-availability-and-reservation.md) (a row read `FOR UPDATE` with `populate_existing`)

## Context
SCRUM-96 and SCRUM-95 were changed after review. A check of `main` against their current text found three gaps.

1. **SCRUM-96 AC2**, and SCRUM-95's "changed after review" note, say an event is active only when it has a coordinator and one of six statuses. A submitted event nobody holds yet is only in the Lead's queue, and moves to the active list once it is assigned. `list_active_requests` read `ACTIVE_STATUSES` alone (ADR-0041 decision 5). So an unassigned request was in both lists, shown with `coordinator: null`, and the web app showed it as "Not assigned" with a link to the queue (ADR-0062 decision 2).
2. **SCRUM-96 AC3** says the Lead sees every Event Coordinator's current assignments, and "a coordinator with no active events is still listed, shown with 0, so the Lead can see who is free". The story's Workload clarification adds that leaving them out "would hide exactly the coordinators who are free". The workload was built from the active events, so an idle coordinator was missing (ADR-0041 decision 6), and the page showed no count, because the frontend may not count for itself (ADR-0062 decision 4).
3. **SCRUM-95's AC for several Leads:** "If two Leads try to assign the same request at the same time, the first assignment is kept and the second is refused with a message that the request has already been assigned. The request still has exactly one coordinator." The story marks this as a team assumption, since the customer didn't say. `_request_waiting_for_the_lead` read the request with no lock. Two Leads could both find it unassigned, and the second commit overwrote the first. ADR-0036 had recorded that as "last write wins", with a row lock as the fix "if that stops being acceptable".

## Decision
1. **An event is active when it has a coordinator and is in one of `ACTIVE_STATUSES`.** `_active_requests_newest_first` filters on `coordinator_id IS NOT NULL` as well as the statuses, and both Lead lists read it. `ACTIVE_STATUSES` is unchanged and is still the status guard a reassignment checks: a reassignment already refuses an event with no coordinator before it looks at the status (ADR-0041 decision 1). `ActiveRequest.coordinator_name` is now a `str`, never `None`, and the route's `coordinator` is never `null`.
2. **The workload lists every Event Coordinator.** It starts from `auth.services.list_user_ids_with_role(Role.EVENT_COORDINATOR)` and names them with `get_user_full_names`. Both already exist, so the events module still imports no auth model. Each active event is added to its holder's entry, and an idle coordinator gets an empty list. Every holder is an Event Coordinator: the first assignment and a reassignment both accept only that role, and no route changes a role. Leads, Venue Staff, Technical Support, Safety Officers and organisers are never listed.
3. **The backend sends `active_count` for each coordinator** (the team's decision, 31 Oct). The route sends `len(assigned)` next to the events, so the web app shows the number as sent, 0 included, and counts nothing itself (`frontend/CLAUDE.md`, "No client-side counting"). It is worked out in the route, not stored on `CoordinatorWorkload`, so the count and the list can't disagree.
4. **The first of two simultaneous assignments is kept.** `_request_waiting_for_the_lead` reads the request `SELECT … FOR UPDATE` with `populate_existing`, as equipment reservations (ADR-0037) and venue booking decisions (ADR-0084) do. The second Lead's read waits until the first commits, then finds the coordinator and gets the existing `409`. `populate_existing` matters because a copy the session loaded earlier may predate the other commit, and the locked row has to overwrite it. The lookup keeps `_event_request_for_staff`'s scope: the reference ignores case and spaces, and a draft is a `404` (ADR-0024). Only the history entry and notifications of the first assignment are written.
5. **The second Lead's message stays "This event request already has a coordinator."** (`409`, `conflict`). It already says the request has been assigned, which is what the AC asks for. A Lead who assigns a request someone else assigned a minute earlier gets the same answer, and that answer is right in both cases. *Agreed by the team (31 Oct):* the alternative is a separate message for the race, which the backend can't tell apart from "assigned a minute ago".
6. **The workload stays ordered by coordinator name, then id.** *Agreed by the team (31 Oct).* The alternative is to put the idle coordinators first, since the view exists to find someone free. Nothing in the ACs asks for that, and a fixed order by name is easier to scan.
7. **The empty-workload message appears only when there is no Event Coordinator account,** and says so: "There are no Event Coordinators." It used to say "No coordinator has an active event request.", which can't be the reason any more. *Agreed by the team (31 Oct).*
8. **The web app shows the count on each coordinator's card** ("0 active events", "1 active event", "3 active events"), and the event list under it only when there is one. "No active events." is gone, because the 0 now says it. Every active-event card now has the reassign form; the "Not assigned" text and the "Assign from the queue" link are gone.
9. **The queue is not re-read when an assignment is refused.** It could be: invalidating the Lead's queries on error as well as on success needs no code-specific branch. But each queued request's card holds its own refusal, so re-reading the queue would unmount the card that shows the message. The Lead would see the request vanish without being told it was already assigned, and AC4 asks for that message. The queue is still re-read after every successful assignment, and the next read after a refusal drops the row. *Default to review.*

## Consequences
- No migration.
- The response shapes changed: `coordinator` on the active list is never `null`, and each workload entry has `active_count`. Idle coordinators appear with `"active_count": 0, "event_requests": []`. The web app's types, its mock (`frontend/src/mocks/handlers/lead.ts`) and the contract tests (`frontend/src/integration/lead.int.test.ts`) changed in the same branch. The todos for the active list, the workload and the assignment's `409` and `404` are real tests now. They run when the run has a Lead account, as in CI.
- The lock is tested as SCRUM-46's equipment lock is: the other Lead's assignment is staged when the locked read runs, with the session already holding a stale copy. The test goes red without `with_for_update()` and without `populate_existing`. SQLite ignores the lock, so the test shows the read is locked and fresh. It can't show two transactions queueing. The contract test's `409` is the sequential case: the integration suite can't stage two Leads at the same instant.
- Reassignment (`reassign_coordinator`) still reads its event without a lock. Two Leads reassigning the same event at once still end with the later one's coordinator and both entries in the history (ADR-0021 decision 15). SCRUM-96 doesn't ask for more, so it is left as it was; see Revisit when.
- `docs/sprint-3-open-decisions.md` §1.8 (an unassigned event in two lists) and §1.9 (idle coordinators) are resolved by this record. §1.10 (the previous coordinator's notice) was settled by SCRUM-96's own clarification ("reusing the existing request assigned type is acceptable"). §1.14 (what "active" means) was settled by AC2's six statuses plus decision 1 here.

## Revisit when
- A role can change, or a non-coordinator can hold an event. Decision 2's "every holder is an Event Coordinator" would break, and the workload would need to say how such an event is shown.
- Two Leads reassigning the same event at once becomes a real problem: give `reassign_coordinator` the same locked read.
- The customer says what the second Lead should be told, if it isn't decision 5's message.
