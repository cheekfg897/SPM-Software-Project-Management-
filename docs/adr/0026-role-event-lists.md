# ADR-0026: Each role's events are a list of its own; an empty list carries a message; coordinators open their own and unassigned requests

- **Status:** Accepted; coordinators' list of unassigned requests and their access to them superseded by [ADR-0034](0034-coordinators-see-only-their-own-events.md); the event record gains a `decision` section in [ADR-0028](0028-review-and-decide.md), and a `clarifications` list in [ADR-0029](0029-clarification-requests.md); the Attendee's list (AC5 here, AC7 in Jira now) is [ADR-0044](0044-attendee-events-list.md); Venue Staff's list (AC3 here, AC4 in Jira now) is [ADR-0085](0085-venue-staff-event-list.md)
- **Date:** 2026-09-26
- **Story:** SCRUM-24 See the events my role is involved in
- **Extends:** ADR-0012, ADR-0018, ADR-0020

## Context
SCRUM-24 gives every role a list of the events it is involved in. Its eight ACs: an Event Organiser sees their client organisation's events (AC1); an Event Coordinator sees events assigned to them, and separately the submitted events not yet assigned to anyone (AC2); Venue Staff see events with a booking request or a booking against a venue they are responsible for (AC3); Technical Support see events that have an equipment request (AC4); an Attendee sees the confirmed events they have registered for (AC5); every list shows event name, date, time and status (AC6); opening an event from the list shows the detail view with only the sections that role may see (AC7); a role with no matching events is told so, rather than shown an empty list (AC8).

Some of this already exists. The organiser's list (`GET /api/events/requests`, ADR-0020) and the coordinator's assigned list (`GET /api/events/requests/assigned`, ADR-0018) cover AC1 and half of AC2. The organiser's detail view (`GET /api/events/requests/<reference>`) covers AC7 for organisers; ADR-0012 deferred the other four viewers to the stories that create each relationship, and named SCRUM-24 as the owner of the lists themselves.

What's still open:
1. **One route or several.** A single `/mine` that dispatches by role, or a route per role list, matching the existing `/assigned` and `/awaiting-equipment` pattern.
2. **What "unassigned" means**, given SCRUM-20 adds a `draft` status with no coordinator either — a draft must never reach a coordinator's list.
3. **What "has an equipment request" covers**, against SCRUM-38's list of equipment Technical Support still have to act on. The two answer different questions: SCRUM-38 is a queue of upcoming work; AC4 asks what events Technical Support are involved in at all, including ones that have already run or whose equipment is fully arranged.
4. **How "none" is expressed**: an empty array with no explanation looks the same as a list that hasn't loaded, or one that's broken.
5. **Which detail sections each role gets**, and how a viewer's identity picks the right lookup instead of a flag argument.
6. **AC3 and AC5 can't be built yet.** Venue Staff have no link to a venue they're "responsible for", and there are no bookings (SCRUM-42) to check against; there are no attendee registrations (SCRUM-52) either. Building a route that could only ever return an empty list would tell a Venue Staff or Attendee user "you have none" when the truth is "this isn't wired up yet".
7. **Picking up an unassigned request.** SCRUM-24 shows the list; assigning oneself to one of it is a separate action (ADR-0018 flagged it, ADR-0021's reassignment 87-6 is the nearest existing mechanism) with no AC here.

## Decision
1. **Per-role routes, not a `/mine` dispatcher.** Keep `GET /requests` (organiser) and `GET /requests/assigned` (coordinator) unchanged; add `GET /requests/unassigned` (coordinator) and `GET /requests/with-equipment` (Technical Support). This matches the existing `/assigned` / `/awaiting-equipment` pattern, gives each list the tightest `@requires_role`, and AC2 already asks for two separate coordinator lists rather than one merged view.
2. **AC1 and the assigned half of AC2 are unchanged.** `list_event_requests_for_organiser` and `list_event_requests_for_coordinator` keep their existing behaviour; only AC8's message is added on top.
3. **Unassigned means `status == submitted AND coordinator_id IS NULL`.** A `draft` (SCRUM-20) also has no coordinator, but a draft is the organiser's alone until they submit it; only `submitted` requests are offered. `_awaiting_assignment()` names this condition once, so the unassigned list and the coordinator's detail view can't disagree about what "unassigned" means.
4. **The equipment list is every event with at least one equipment line, whatever its status, date or line state.** One row per event (an `EXISTS` on `equipment_lines`), newest first. SCRUM-38's `/awaiting-equipment` stays the actionable subset — events with a line still `requested`, upcoming, not already decided against — because that is what "awaiting my action" means; AC4's "have an equipment request" is broader and answers a different question. `list_event_requests_with_equipment` reuses `_list_event_requests_newest_first` with `EventRequest.equipment_lines.any()`, wanting events rather than SCRUM-38's line-level grouping.
5. **The list lives in the events module, not equipment.** `EventEquipmentLine` belongs to events (SCRUM-37, ADR-0019); the equipment module importing events to query it would be the cycle ADR-0022 already ruled out.
6. **Every list row carries the AC6 fields.** The organiser, assigned and unassigned lists dump the full `EventRequestSchema`, as the existing lists already did. Technical Support's row is deliberately smaller: `EVENT_LIST_FIELDS = (*EQUIPMENT_EVENT_FIELDS, "status")` — the same name, date and times their own `/equipment` detail view shows, plus the status that view doesn't carry. Their detail view (`GET /requests/<reference>/equipment`, ADR-0019) isn't widened to match; the list shouldn't show more than the record it links to (AC7).
7. **AC8 — a list with nothing in it says so.** `{"event_requests": [], "message": "<list-specific sentence>"}`, with `message` present only when the list is empty; a non-empty list carries no `message` key at all. This copies `search_venues`'s precedent (SCRUM-35 AC4) rather than inventing a new shape, and is additive: nothing that reads `event_requests` and ignores unknown keys breaks. Every list uses the same `event_requests` key, including Technical Support's, so a client doesn't special-case one list's response shape. The four messages: *"Your organisation has no event requests yet."* (organiser), *"No event requests are assigned to you yet."* (coordinator, assigned), *"No submitted event requests are waiting for a coordinator."* (coordinator, unassigned), *"No events have an equipment request yet."* (Technical Support). SCRUM-38's `/awaiting-equipment` is not touched: it's an action queue, not one of SCRUM-24's role lists.
8. **AC7 widens the event record to Event Coordinators**, not to Technical Support (whose detail view is already `/equipment`) and not to Venue Staff or Attendees (no AC, and no data to scope by yet). `GET /requests/<reference>` now allows `event_organiser` and `event_coordinator`. A coordinator sees the same sections the organiser does — the request, its status, the assigned coordinator's contact, its equipment lines — for a request assigned to them, or a submitted one no coordinator has yet (so they can read what is waiting for a coordinator). Anything else, including another coordinator's request or an unassigned one that isn't submitted, gets the existing `EVENT_REQUEST_NOT_FOUND_MESSAGE` 404 (ADR-0012), so a coordinator learns no more about a request outside their reach than an organiser does about another organisation's.
9. **`_visible_to_coordinator(id) = _assigned_to(id) OR _awaiting_assignment()`**, mirroring how `_visible_to_organiser` is the one place ADR-0020 decides an organiser's scope. `_assigned_to` is extracted from the body of `list_event_requests_for_coordinator` (behaviour unchanged) so the list and the new detail view can share it, exactly as `_awaiting_assignment` is shared between the unassigned list and the detail view. One condition, used by both, means the list and "can I open this one" can never drift apart.
10. **The route picks the service, not a `viewer_role` flag.** `get_my_request` reads `g.current_user_role` and calls `get_event_record_for_coordinator` or `get_event_record_for_organiser`. A boolean or role parameter threaded into one service would violate CONVENTIONS' no-flag-argument rule and complicate a function that only ever runs one of two unrelated queries. Unlike `list_equipment_lines`'s `viewer_role` argument, the two scopes here are separate conditions, so two functions read better than one with a flag, and the organiser's existing service and its tests stay untouched.
11. **No stub or route for AC3 or AC5.** Nothing is added for Venue Staff or Attendees. A `# TODO: SCRUM-42 adds Venue Staff's list (AC3) and SCRUM-52 the Attendee's (AC5), in the same shape (ADR-0026).` sits above the list routes so the gap is visible in the code, not just in this ADR. An always-empty route would be worse than no route: it answers "you have none" when the honest answer is "this isn't built yet".
12. **Picking up an unassigned request is out of scope.** Nothing here lets a coordinator claim one; that's a follow-up ticket. AC7 only lets them *read* an unassigned request, not act on it.
13. **No migration.** `event_requests.coordinator_id` and `event_equipment_lines.event_request_id` are already indexed (SCRUM-30, ADR-0018; SCRUM-37, ADR-0019); `status` is not, but the unassigned list is small, so no index is added. The new queries add no new column.
14. **Route names.** The existing `get_my_request` view name is kept (ADR-0020 precedent) rather than renamed to something that also covers coordinators, since renaming would touch every existing test of it for no behavioural gain. The new views are named for what they list: `list_unassigned_requests`, `list_requests_with_equipment`.

## Consequences
- A frontend reads `event_requests` from any of the four lists and checks for `message` when the array is empty, rather than inferring "none" from an empty array (which can't be told apart from "still loading").
- Any Event Coordinator can read the full detail of any unassigned submitted request, including its equipment lines, before it is theirs. They still can't add equipment to it (ADR-0019: only the *assigned* coordinator may) or reassign it (87-6: only the *current* coordinator may) until it is assigned to them.
- Technical Support's list includes events that have already taken place, or whose equipment is already fully arranged; SCRUM-38's `/awaiting-equipment` remains the place that narrows to what still needs doing.
- Technical Support's equipment detail view (`/equipment`) still carries no `status`, even though their list row now does; a viewer moving from the list to the record loses that one field.
- `/awaiting-equipment` still has no AC8 message; an empty action queue and "nothing assigned to me yet" are different situations and are left to read differently.
- No migration ships with this story.

## Deferred
- **AC3** (Venue Staff's list) waits on SCRUM-42 (booking requests and bookings) and a staff-to-venue link that doesn't exist yet.
- **AC5** (the Attendee's list) waits on SCRUM-52 (attendee registrations).
- An event's history is its own route, `GET /api/events/requests/<reference>/history` (SCRUM-33, ADR-0025), not a section of the record. A venue booking section (SCRUM-42) isn't part of any detail view yet.
- Showing the organiser's contact details to coordinators was not asked for and isn't added.
- Picking up an unassigned request is a follow-up ticket, not this one.

## Revisit when
- SCRUM-42 lands: add Venue Staff's list and widen bookings into the coordinator's and organiser's detail views.
- SCRUM-52 lands: add the Attendee's list.
- Picking up an unassigned request is requested: decide what claiming one does to `_awaiting_assignment`'s result.
- Technical Support ask for `status` on `/equipment`, or a message on `/awaiting-equipment` when it's empty.
- SCRUM-31 lands: its coordinator-review work can reuse `get_event_record_for_coordinator` and `_visible_to_coordinator` rather than re-deriving coordinator scope.
- The customer asks for the unassigned list ordered oldest-first, or by event date rather than newest-submitted-first.
