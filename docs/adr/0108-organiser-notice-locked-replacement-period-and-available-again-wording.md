# ADR-0108: The organiser is told when a venue sends their confirmed event back, a replacement keeps the flagged booking's period, and "available again" names the venue and the event

- **Status:** Accepted; telling the organiser, locking the replacement's period and the "available again" wording follow the Product Owner's decisions of 25 Oct; the organiser's wording and kind (decision 1), refusing each moved time field after the same-venue check (decision 3), reading "went back from Confirmed" from any of the event's flags (decision 6) and one notice per event (decision 7) are defaults to review
- **Date:** 2026-10-26
- **Story:** SCRUM-92 Flag bookings affected when a venue becomes unavailable (AC3, AC6, AC8, "Changed after review", 25 Oct)
- **Extends:** [ADR-0053](0053-flag-bookings-when-a-venue-becomes-unavailable.md), [ADR-0088](0088-replacing-a-flagged-venue-in-the-web-app.md), [ADR-0100](0100-on-hold-same-venue-and-available-again.md) (supersedes its decision 8, the wording, and the "one notice per arrangement" part of decision 7)

## Context
On 25 Oct the Product Owner changed three of SCRUM-92's criteria:

- **AC3:** "The Event Organiser is notified when a Confirmed event goes back to Approved because a venue became unavailable", naming the event and the venue (customer: Week 9, A13). Only the assigned coordinator was told before (ADR-0053 decision 9).
- **AC6:** "The replacement is locked to the flagged booking's date and times, so it cannot be used to move the event." The replacement used to take any period (ADR-0053 decision 10), and the web app filled the form from the flagged arrangement but let the coordinator change it (ADR-0088 decision 4).
- **AC8:** "Available again" is sent only when nothing else still makes the venue unavailable for the booking, and names the event: "<venue> is available again for <event>. Your original booking stands.", adding that the event still needs Safety Review and confirmation when it went back from Confirmed to Approved. ADR-0100 already waited for the arrangement's last flag; its detail named the venue, the arrangement's purpose and its period.

## Decision
1. **AC3: the organiser who submitted the request is told, once per event, after the flags' commit.** `record_alternative_venue_needed` now returns whether it sent the event back to Approved; the venue module keeps that on each notice and, after the commit (ADR-0015), calls `notify_organiser_venue_unavailable` for each event sent back. When one block flags two of an event's arrangements, only the first finds the event Confirmed, so the organiser hears once. Only the submitting organiser, as for the other decisions on their request (ADR-0028) and confirmation (ADR-0051). **Default to review:** the notice reuses the `alternative_venue_needed` kind, whose message, "A venue booked for your event is unavailable. The event needs an alternative venue.", is true for the organiser too, so no migration is needed. The detail names the venue and the event and says what happened to the status: `Main Hall became unavailable for Partner Summit, so the event has gone back from Confirmed to Approved for its venue to be reviewed. It has not been cancelled.` Venue Staff's note stays out of it, as it stays out of the organiser's history (ADR-0053 decision 7); the flag and its reason on the record are SCRUM-24's.
2. **AC6: a replacement for a booking whose venue became unavailable keeps that booking's date and start and end time.** The backend compares the request's `starts_at` and `ends_at` with the flagged arrangement's as instants (ADR-0009), so the same period written in UTC or with no offset is accepted, and an overnight booking keeps its end date too. Another period is a `400` on each time field it moves, with the period in business time: "A replacement keeps the date and times of the booking it replaces: 2026-11-01 09:00 to 2026-11-01 12:00."
3. **Default to review: the period is checked after the same-venue rule,** so a replacement at the venue it replaces is refused on `venue_id` alone, whatever its period (ADR-0100 decision 5), and fixing that shows any period refusal next.
4. **The lock applies only while the arrangement needs an alternative venue** (`needs_alternative_venue`), so one flagged both ways is locked too. A replacement for an arrangement flagged only after a change keeps ADR-0100 decision 5: it may stay at its venue for a new period, because a time change is what flagged it and a replacement is how that flag clears (Product Owner, 25 Oct, 6.4).
5. **The web app prefills and locks the period.** "Find another venue" already opens the search set to the flagged booking's date and times, and "Request this venue" already fills the form from it (ADR-0088 decisions 3 and 4). While the arrangement replaced needs an alternative venue, the form's Starts and Ends are read-only and say "Fixed to the booking it replaces. In Singapore time." They are still sent, so the backend checks them. While the event's list doesn't hold the arrangement, or it is flagged only after a change, the period stays open. A refusal shows under each time field, and the event's list is read again after any answer, a refusal included, so the form sees a change it was refused for. The booking mock refuses another period the same way.
6. **AC8: the "available again" detail names the venue and the event,** `Main Hall is available again for Partner Summit. Your original booking stands.`, and the kind's message is now "A venue that was unavailable for your event is available again." The events module writes the detail, since it holds the event's name and history; the venue module passes the venue's name. **Default to review:** "It still needs Safety Review and confirmation." is added when any of the event's `alternative_venue_needed` history entries says it sent the event back to Approved (`returned_to_planning`). It is read for the event, not the one arrangement, because the sentence is about the event: one venue's flag may have sent it back and another's be the one clearing. A flagged event can't be confirmed again (ADR-0053 decision 13), so the sentence can't follow a newer confirmation.
7. **Default to review: one notice per event, however many of its arrangements at the venue are freed.** The detail no longer names an arrangement or its period (the Product Owner's wording names only the venue and the event), so a second notice would say the same. The arrangement left with no flag is still found as ADR-0100 decision 7 finds it.
8. **"Only when nothing else still covers the booking" stays as built** (ADR-0100 decision 7): an arrangement that another block, or the deactivation, still flags gets no notice. Tests now pin two overlapping blocks and a block removed while the venue is still deactivated.

## Consequences
- An organiser may hear about one venue twice: when their confirmed event goes back to Approved here, and when the coordinator confirms it again (ADR-0051).
- A coordinator with two arrangements at one venue hears once when the venue is free again.
- The replacement can no longer move an event; moving it is a change request (SCRUM-56, SCRUM-57).

## Revisit when
- An arrangement is raised at a venue during a block that already covers it: the block didn't flag it, so lifting another, later block over it would send "available again" while the first still covers it. Flagging a request raised into a block (or refusing it) would close this; it is outside SCRUM-92's criteria, which flag what a new block cuts into.
- The customer wants the organiser told when the venue is available again, or when a replacement is approved.
- SCRUM-59 lets Venue Staff reconfirm a booking: decide whether a change-flagged replacement still takes a new period.
